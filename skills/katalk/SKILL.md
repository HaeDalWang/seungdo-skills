# 카톡 스타일

고객사 담당자에게 메신저로 바로 보낼 메시지. 보통 기술직이지만 직군을 가정하지 않는다. 사용자가 그대로 복사해서 보낸다.

## 형식

```
[관찰한 사실] + [되묻기 ~인가요??]
[이유 한 줄, 확신 없으면 "~날 수 있어서"] + [해결책 한 줄 ~하시면 됩니다!]
```

- **2~3줄.** 한 줄이 길어도 괜찮지만 줄 수는 늘리지 않는다
- **사실 먼저.** "지금 ~는 ~인데 ~가 안보여서요" — 우리가 실제로 본 것
- **되묻기.** "혹시 ~인가요??" / "~로 이해하면 될까요??" — 단정하지 않는다
- **해결책은 한 줄, 복붙 가능하게.** 리소스 이름, DNS, 파일:행, 설정값을 그대로 적는다
- **말투.** "~요 / ~습니다 / ~해요", 끝은 "!" 로 가볍게. 물음표 두 개(`??`)도 사용자 스타일
- 코드블록 하나로 감싸서 준다. 사용자가 그대로 복사한다

## 넣지 않는 것

- 고객 리소스 해설 — "그쪽 거라 그쪽이 더 잘 안다". 해설 대신 "이렇게 보이는데 맞나요?"
- 근거 나열, 문서 인용 여러 개, 배경 설명 — 필요하면 링크 하나
- 사과, 서론, "검토해봤는데요" 같은 쿠션을 두 줄 이상
- 고객이 이미 아는 것, 이미 한 것
- 추정을 사실처럼 쓰기. 확신 없으면 "~날 수 있어서", "~인거 같아요"

## 보내기 전에

- 메시지에 들어가는 **사실은 이번 세션에서 직접 확인한 것**이어야 한다 (명령 결과, 타임스탬프)
- 고객이 작업 중이면 **중간 상태를 장애로 단정하지 않는다** — 배포는 시간이 걸린다. "혹시 ~ 에러 났나요??" 로 묻는다
- 고객 의도를 모르면 먼저 묻는다. 막아둔 게 의도일 수 있다 (예: 망 오픈 전이라 DNS 일부러 안 바꿈)

## 사용자가 초안을 주고 "검토"라고 하면

- **파일을 고치지 않는다.** 말로만 짚는다
- 문제만 순위대로: 🔴 사실 오류·빠지면 사고 / 🟡 오해 소지 / 🟢 오타
- 각 항목에 **바꿀 문장 한 줄**만 제안. 전체를 다시 쓰지 않는다 (요청하면 그때)
- 사용자 오타는 굳이 고치지 않는다. 사실관계를 바꾸는 오타만 짚는다
- "나머지는 정확합니다" 로 끝낸다

## 예시

실제로 한 번에 원인이 확인된 메시지:

```
혹시 apply 출력에 aws_lb_target_group.traefik_alb 에러 나있나요?? 지금 NLB는 active인데 NLB→ALB 타겟그룹이 prod VPC에 안보여서요
dev 쪽에 같은 이름(traefik-alb-tg-443/80/8000)이 이미 있어서 이름 겹치면 DuplicateTargetGroupName 날 수 있어서 그때는 name에 ${local.env} 넣으시면 됩니다!
```

사실(NLB active, TG 없음) → 되묻기(에러 났나요??) → 가능성(날 수 있어서) → 해결책(`${local.env}`).

나쁜 예 — 같은 내용을 해설로 쓴 것:

```
검토해본 결과 타겟그룹 생성 단계에서 문제가 발생한 것으로 판단됩니다.
AWS 에서 타겟그룹 이름은 계정과 리전 단위로 유일해야 하는데,
dev 와 prod 가 같은 계정을 쓰고 있어서 ...
```

→ 단정, 해설, 줄 수 초과.

## 카톡이 아닌 경우

티켓(Zendesk) 회신이나 고객에게 첨부할 문서는 이 스킬 대상이 아니다. 그건 md 로 따로 쓰고, 실행 문서(작업순서)와 근거(README)를 나눈다.
